# 12 — User Interface & Canvas: desktop (shell) and mobile

How the user sees and moves through the workspace: the native shell and its widget stack, the
window metaphor, the spatial canvas and its encoding, theming, the AI bubble, how actions are
confirmed, the mobile UI, and the accessibility commitments.

Two user interfaces ship over the same backend:

- **Desktop — the native shell** (`sovereign`), the only desktop UI since 2026-10-09 (ch. 02).
  It is the reference for desktop behaviour, and the sections below describe it unless they say
  otherwise.
- **Mobile — the Svelte UI** in the Android app, hosted by Tauri. It has its own section
  (*Mobile UI*); where a desktop section's subject also exists on mobile, the difference is
  stated there.

The Svelte desktop layout (`sovereign-tauri`) is frozen and not shipped. It is mentioned only
where an earlier design was built there.

## Native shell stack

**Status:** ✅ Built (code: `crates/sovereign-shell/`).

The shell draws everything — canvas and chrome — with one renderer, so there is no seam
between a canvas engine and a widget toolkit.

| Concern | Choice |
|---|---|
| Rendering | vello 0.9 on wgpu |
| Text shaping and layout | parley 0.10 |
| Windowing and input | winit 0.30 |
| Widgets, layout, focus, scrolling | Own thin layer on the above. Manual layout; each panel computes its geometry in one function shared by the painter and the hit-test, so the two cannot drift. No taffy yet. |
| Accessibility | accesskit 0.24 + accesskit_winit 0.32 |
| Embedded web page | `wry` child webview over the window; vello draws the browser chrome (ch. 10) |
| Clipboard, QR | arboard; qrcode drawn as vello cells |

The UI is laid out in logical pixels and scaled by the display scale factor times a user UI
scale, so it stays crisp on high-DPI screens. The widget layer was a deliberate choice over
Masonry/Xilem (pre-1.0, mid-refactor onto a different vello version) and GPUI (a second
renderer beside the canvas). The cost accepted: text input, IME, focus, scrolling and
accessibility are ours to build.

**Graphics backends: no OpenGL on Windows — built in v0.0.12** (Céline, 2026-10-24: "Retirer sous
Windows maintenant", confirmed after the measurement below: "on l'enlevait à moins que tu aies une
objection"; merged `3d1a1a4`, 2026-10-25). On Windows the
shell's wgpu instance is created with DirectX 12 and Vulkan only, so it no longer creates an OpenGL
context; until v0.0.11 every backend was enabled and wgpu opened a hidden WGL context at start even
though the adapter used was DX12 or Vulkan. Every other setting of the instance is unchanged. On
Linux and every other platform the default set, OpenGL included, is unchanged. One function builds
the shell's render context, for the window and for the headless frame alike.
- `WGPU_BACKEND`, when set, decides on every platform, as before: a development switch (PANDA2's
  choice). A set value that names no backend wgpu knows, or is empty, gives no backend and so no
  adapter, as wgpu does; there is no silent fallback to the platform default (PANDA2's choice,
  2026-10-25).
- **`WGPU_BACKEND=gl` is not offered to users as a fallback**: a start with OpenGL only panicked
  once in six on PANDA2 (wgpu's GL context lock during vello's parallel shader initialisation). A
  machine with neither DX12 nor Vulkan fails to get an adapter, as before; that path is not
  redesigned here. Under OpenGL on Linux the same initialisation is a backlog item.
- What it buys: measured on PANDA2 before the change, start was about 75 ms (3 %) faster without
  OpenGL; the gain is mostly the hidden GL context and the driver's WGL code path, not start time.

**Text fields.** ◐ One text field serves the shell: the document editor's (*The document editor —
contract (C-TEXT)*), opened as a single-line field for the document title, the new-thread name,
the lane rename and, since v0.0.12, the chat composer and the search query (item 21, below) and
the device renames (items 14 and 19, ch. 05 *Device names*). It
gives caret movement, selection, Backspace and Delete anywhere, word and line movement, undo,
copy, cut and paste, input methods, bidirectional text and horizontal scroll; no second
text-editing implementation exists. The other text fields are still append/backspace buffers
with the caret pinned at the end (no selection, no paste, no input method): the login and
first-run forms, the recovery wizard's new passphrase, the browser's address bar, and the comms
account form and the email compose form (both dormant). Moving the password
fields onto the editor's password field is its own contract, with the clipboard and reveal rules
(backlog).

**The chat composer and the search field — built in v0.0.12** (item 21, Céline, 2026-10-23:
today a typo cannot be corrected in place). Choices marked
PANDA2's were made by the PANDA2 maille on 2026-10-23 and 2026-10-24; Céline can overturn them.
- Both are the editor's single-line field, with the shell's shared key routing and the field
  clipboard, as the rename and new-thread fields are. An input method's pre-edit is drawn in
  place while the window is on top, and its commit is inserted once.
- **Enter** in the composer sends the trimmed text when it is not blank, then empties the field;
  a blank text sends nothing. Enter in the search field opens a chat with the trimmed query sent,
  as before; a blank query only closes the search window. **Escape** closes the window; during an
  input method's composition the first Escape ends the composition and the next one closes
  (PANDA2's choice).
- **An Enter during a composition stays in the field**: it commits the composition and nothing
  else happens; the next Enter sends (PANDA2's choice). This is a rule of the field itself, so the
  lane rename and the new-thread name inherit it.
- The search results refresh on every edit (typing, deleting anywhere, paste, cut, undo, an input
  method's commit), not on caret movement or selection.
- Each field is a text input in the accessibility tree, named "Message" and "Search", with its
  value and selection; the visible placeholders are unchanged (PANDA2's choice).
- Nothing new leaves memory: the message is kept nowhere but the field until it is sent, and the
  field's undo history stays in memory and is dropped with the field. Emptying the field after a
  send is an edit of the field, so **Ctrl+Z in the emptied composer brings the sent message back**
  (the code author's choice; Céline, 2026-10-24: "Garder").
- A pasted multi-line text becomes one line (a single-line field turns line breaks into spaces): a
  known consequence, not a goal. Multi-line messages are a question for Céline, for later.
- Unchanged: what is sent to the orchestrator, the chat history and the search results. The
  composer stays editable while a reply is pending.

*Status:* ● built in v0.0.12 item 21 (merged `9e93a9b`, 2026-10-24; tests `chat_field_tests.rs`,
`field_enter_tests.rs`, `sovereign-editor/tests/f_field_enter_composing.rs`).

*Replaces v1.x:* "UI framework: Iced 0.14" — retired in v0.0.3; the Svelte + Tauri UI was the
only UI until the native shell became the default in v0.0.8, and the shell has been the only
desktop UI since 2026-10-09 (ch. 02).

## Floating multi-window

**Status:** ✅ Built (code: `crates/sovereign-shell/src/app.rs`, `panels.rs`).

Every panel is a free-floating window over the live canvas — documents, version history,
inbox, chat, search, settings, models & trust, personal data, browser, devices & sync, alerts
on changes from your devices, previous values of synced items. Windows overlap, are dragged by their title bar, come to the front on
click, close with × or Esc, and open in a cascade. Launchers open-or-focus (a second press
closes); a document opens-or-focuses by id, so several documents can be open at once. The
chat opens anchored to the bubble, because the chat *is* the conversation with it. The
browser's webview is shown only while its window is on top and no modal is up.

| Key | Opens | Key | Opens |
|---|---|---|---|
| `c` | Chat | `b` | Browser |
| `i` | Inbox | `d` | Devices & sync |
| `s` | Settings | `a` | Alerts on changes from your devices |
| `m` | Models & trust | `v` | Previous values of synced items |
| `p` | Personal data | `g` | Enrol a recovery guardian |
| `e` / `w` | Email setup / compose (switched off since v0.0.9; they open nothing) | `Ctrl+F` | Search |
| | | `Ctrl+S` | Save the document being edited |

◐ `Ctrl+N` (new document) and `Ctrl+B` (browser) are not bound.

*Replaces:* the first shell cut's single centred modal per panel (2026-06); the floating
metaphor matched the Svelte desktop UI (now frozen), at Céline's request.

## Context menu

**Status:** ✅ Built (code: `crates/sovereign-shell/src/app.rs`).

Right-click opens a popup at the cursor; it dismisses on an outside click, Esc or scroll.

- **On a card:** Open · Pin / Unpin · Skills › · Delete
- **On empty canvas:** New lane · New document (in the lane under the cursor).

The `+` button opens the canvas menu. Pinning persists and is low gravity. **Delete is one
click** (Céline, 2026-10-17; ch. 03, *Soft delete and 30-day purge*): the document goes to the
trash, and a notice at the foot of the canvas says "Moved to the trash — it can be restored for
30 days" and offers **Undo** for 10 seconds; after that it is restored from Settings → Trash. A
document found already in the trash says "Already in the trash", with no Undo. Delete is refused,
with "This document has unsaved edits. Save them first.", while a window holds unsaved edits of
it. The same guard holds for the documents waiting for a thread in the Alerts window (ch. 03,
*Thread deletion*): T trashes the selected one, Shift+T or "Trash all" its group, and one document
with unsaved edits refuses the whole group, nothing moved (v0.0.12 lot 1). See *Confirmation UX*
for how this sits against Action Gravity.

### Skills from the context menu

**Status:** ◐ Partial — the submenu and content-transform skills work; skills that need the
database or a model do not run in the shell.

**Skills ›** lists the 24 core skills (ch. 11). Picking one runs its first action on the
document and shows the result, or the error, in a notice. This replaced the per-document
skills sidebar of the Svelte desktop UI (now frozen), at Céline's choice. In the shell,
skills receive no database or model handle, so search, backlinks, thread summary and similar

## Documents

**Status:** ◐ Partial — read, edit, save, history and restore are built. Since 2026-10-19
(Céline's decision of that day; released in v0.0.11) the C-TEXT editor below is the shell's only
document editor, in every build; the plain text edit is removed.

**Decided 2026-10-10 (Céline): the document editor is built in-house on parley**, rendered by
vello like the rest of the shell, with no webview. A spike showed a webview editor can be
isolated on Windows only with four workarounds outside wry's API, ~185 MB per editor, no vello
overlay above it and no Wayland support (private spike record). **Method: tests first.** The
suite that can break the editor is written before the editor, by a different author than the
editor's, and asserts invariants only — nothing typed is lost; unknown block types (ch. 03)
pass through intact; no plaintext reaches the disk outside the encrypted store; no network;
input methods, grapheme clusters, bidirectional text, undo/redo, very large documents, a
document changed by sync while open, accessibility. The editor is built to make that suite
pass. Prerequisites: the v2 block schemas (ch. 03) and the text-field contract.

A document window shows the title and body, with a provenance accent. The body is editable as
soon as the window opens, with no Edit step: the editor (*The document editor — contract
(C-TEXT)*, below) saves by itself, `Ctrl+S` saves at once, and closing the window (× or Esc)
saves first. History lists the document's versions, read from the document service; restoring
one goes through the store, which verifies the snapshot's integrity before applying it (ch. 03).
A row whose integrity check failed says so on its second line ("can’t be verified"), on screen
and to a screen reader, and is not restored; older, unsigned versions carry no mark. A history
that cannot be read opens no window, and the notice says "This document’s history could not be
read. Nothing was changed; try again in a moment." Since v0.0.13 its first sentence is the document
service's (ch. 03, HR1), which the shell shows and does not copy; the shell adds only its tail.
Without a document service (the
store not unlocked), History does not open, and the notice says "The workspace is locked: log in
to see a document’s versions." (v0.0.12 lot 1, H3–H5). Since v0.0.12 a row received from a
paired device names the device, and a row's message never overlaps its time (item 14, ch. 05
*Device names*). Dragging a card onto another
lane moves the document to that lane's thread, through the document service's stamped move, so the
move reaches the other devices (v0.0.12). The pin is a display preference of each device: it is not
synced (Céline, 2026-10-24).

**History on both hosts — names, not ids.** **Built in v0.0.13** on both hosts: the desktop (the review's
item 19, merged 2026-11-18) and the phone (the C5 line, merged 2026-11-19). Specified 2026-11-18, written by
PANDA2. One rule for the desktop's History and the phone's. Until
v0.0.13 only « Synced from », « Received from » and « Concurrent edit from » named the device, on the
desktop only: « Before sync from {id} », written when a sync replaces an edit made here, showed and read aloud the
52-character peer id, « Restored from {commit id} » showed a raw commit id, and the phone named every
device by its id. What a row says when a version or the whole list cannot be read is in ch. 03,
*History, in v0.0.13*.
- **HN1 — A device is named by its name.** Every row that names a device shows, and gives to a
  screen reader, the name this device's paired list holds for it (ch. 05, *Device names*); « this
  device » for its own id; for a device no longer paired, « … » and the id's last 8 characters, as
  built on the desktop. Never the whole peer id. « Before sync from {device} » follows this rule like
  the others.
- **HN2 — A version is named by its date and time.** « Restored from {commit id} » is shown as
  « Restored from the version of {YYYY-MM-DD HH:MM} », in local time, in History's format, the date
  and time of the version restored, read in the same document's history. A version no longer found
  there is « an earlier version ». Never a raw commit id. « Restored from backup » stays as it is.
  « Before restoring {commit id} », the version kept before a restore when the document had changed
  since its last version, is shown « Before restoring the version of {YYYY-MM-DD HH:MM} », or
  « Before restoring an earlier version » when that version is no longer found, the same way.
  - **Every row's own time is in local time too,** on both hosts: a row's own time and the time HN2
    names for the same version are the same words. As built, the desktop writes each row's time in
    UTC (one hour early in Switzerland in winter), against AT11. Part of item 19 (this bullet and the
    row before it: the Fable maille, by delegation of Céline (2026-11-14), on 2026-11-18).
- **HN3 — The stored message is unchanged.** The names are given where the row is shown, as item 14
  did, so older versions are shown the same way.
- **HN4 — Restoring the version that is already current says so.** When the version chosen has the
  document's current title and content, nothing is written, no version is added, and the host says
  « This is already the current version. Nothing was changed. » Until v0.0.13 the desktop showed no
  notice.
- **HN5 — On both hosts, from one place.** The names and the dates are made in the document service
  or the crate both hosts link (D16, ch. 01), so the desktop and the phone show the same words for the
  same row.

**New thread — named first, as in the Tauri desktop** (2026-10-17; Céline asked for the title
"as in Tauri" and for the work to continue on threads without her): the new-thread gestures open
a name field (*Thread name…*); Enter creates the thread with that name, Esc cancels, an empty name
creates nothing. **A thread is renamed in place** by double-clicking its lane's label: a name
field opens over it, Enter saves, Esc cancels; the assistant can rename threads too (Céline,
2026-10-18; ch. 03, *Thread deletion and the fallback lane*). A screen reader's Click on a lane's
label opens the same field. ✅ Both built 2026-10-18, released in v0.0.11, in every build.
- **The new-thread prompt.** The canvas menu's *New lane* (the `+` button opens that menu) opens
  a small prompt: the name field, focused, and a *Create* button, inactive while the name is empty
  once trimmed; Tab moves between the two. Enter or *Create* creates the thread with the name
  trimmed, on one line (a pasted line break becomes a space); Esc or a click outside creates
  nothing. No thread exists until it is created. A name already used by another thread is accepted.
- **The rename field.** It opens over the label with the current name selected. Enter saves the
  trimmed name and the label shows it at once; Esc or a click outside cancels; an empty name, or
  the same name, closes it and writes nothing, so it cannot override a rename made elsewhere. The
  rename goes through the one stamped thread write, so the later rename wins across devices (ch.
  03). If the thread was deleted meanwhile, nothing is written and the notice "Thread not renamed"
  says "This thread was deleted meanwhile; nothing was changed." Duplicate names are accepted.
- **Both fields are the editor's single-line field** (caret, selection, clipboard, input methods,
  bidirectional text, horizontal scroll). During an input method's composition, Enter or Esc ends
  the composition and does nothing else; the next Enter creates or saves, the next Esc cancels.
- **Accessible.** The prompt is a dialog named "New thread", holding a text input labelled "Thread
  name" and the *Create* button, announced as disabled while the name is empty; there is no Cancel
  button, Esc closes it. Each lane's label is a button named "Rename thread <name>"; the open
  rename field is a text input labelled "Thread name".

**Title — decided 2026-10-17 (Céline): as in the Tauri desktop.** The title is an editable
single-line field at the top of the document's page — it scrolls with the text, 1.1 × the body
size, semi-bold (revised the same evening, after her manual run) — editable whether or not the
body is in edit mode, shown as *Untitled* while empty, and saved with the body by the same
delayed save. The window's bar keeps the title in small type (14 px, one line, cut with an
ellipsis), so the open document stays named when the page has scrolled. A
new document is created titled "Untitled" and opens with the title field focused and its text
selected, so its name is typed first; Enter or Tab moves to the start of the body, and Shift+Tab
from anywhere in the body comes back to the title. No *Rename…* row in the card menu.
- **One line.** Enter never puts a line break in the title, and a pasted line break becomes a
  space. A title longer than the field scrolls sideways so the caret stays in view; it never wraps.
- **Saved trimmed.** Leading and trailing spaces are trimmed at save; a title of spaces only is
  saved empty. An empty title reads *Untitled* everywhere it is shown (card, window bar, trash,
  search, taskbar, lists, and the phone), while the field shows *Untitled* as a dimmed placeholder
  and the stored title stays empty.
- **Unsaved is unsaved.** A title change not yet saved is an unsaved edit of the window: closing
  it, deleting the card or restoring a version behaves as with an unsaved body.
- **Accessible.** The field is a text input labelled "Title", reached by Tab, announced with its
  value, with the editor's caret, selection, clipboard, input-method and bidirectional-text rules.
- **Read-only stays read-only.** A document opened read-only shows its title as text, not as a
  field.

✅ Built 2026-10-17, released in v0.0.11, in every build since the editor became the only one
(2026-10-19); its contract is T1–T10 (tests `title_tests.rs`, `sovereign-editor/tests/t_title.rs`).

**A personal-data token in a title is shown as its label — built in v0.0.12** (item 8, L1 and L2;
the cloud review of v0.0.11, R18, whose scope Céline confirmed on 2026-10-23; merged `e3e8c6c`,
2026-10-25). Titles are ingested, so they can hold
tokens (ch. 09). The editor's accessible label is the title as drawn: a token is its label, or
its value only while revealed, never its stored form `[pii:…]`. Everywhere else the shell draws
or announces a title — cards, window bars, History, alerts, orphans, trash rows, and what reads a
card's title (taskbar, search, the delete and unsaved notices) — a token is shown as its label, so
search matches the label, not the stored form. With no document service (no-auth mode), or when
the read fails, every token form is shown as `[PII]`: a stored form is never shown when in doubt
(the code author's choice, read by PANDA2). ◐ Limits: card bodies keep the stored form and are not
announced; the cards and the open editor can label one token differently (the service's label set
and the editor's; backlog).

*(The plain text edit these lines used to describe — no caret movement, × or Esc discarding
unsaved changes, a failed save not reported — is removed (2026-10-19). With the editor, nothing
unsaved is lost on any way out: it saves first and asks only when the save fails.)*

**With the editor the only one** (built 2026-10-19 under Céline's decision of that day, released
in v0.0.11):
- **When the editor cannot open a document, no window opens**: there is no other view to fall
  back to. A notice titled "Document" says why, in plain words: "No workspace database is open, so
  the document can't be shown.", "This document couldn't be read, so it can't be shown.", "This
  document is encrypted and this session can't decrypt it. Log in to open it.", or "This document
  can't be shown: <the editor's reason>." It never shows stored JSON or ciphertext, never quotes
  the store's error, and never says or implies that the document belongs to another persona or
  another store. A document the editor can only read (a newer format, over the size cap) opens
  read-only, with the editor's own status line.
- **Every change to an open document reaches its editor.** A change made by the assistant reaches
  it as a sync does ("This document was changed on this device (by the assistant)…"): reloaded if
  it holds nothing unsaved, otherwise kept, its next save resolving against the newer revision
  (*A save that finds the document changed elsewhere*, below). A skill or a restore, which are
  refused while the window holds unsaved edits, reopen the editor on the stored result.
- **A store replaced under open windows leaves nothing of them.** The shell unlocks once per run
  (it has no lock, logout or persona switch); whenever an unlock installs a store while windows of
  another are open, every window showing that store's documents closes (document windows, History,
  Search, Alerts, Previous values, Settings), the editors' sessions end on the store they belong
  to, the copy this process made is cleared (*Clipboard*, below), and the menus, dialogs and the
  delete notice that name its documents go. No prompt is shown, so it looks the same in every
  persona.

### The document editor — contract (C-TEXT)

**Status:** ✅ Built — the shell's only document editor in every build since 2026-10-19, released
in v0.0.11. Specified 2026-10-10; choices marked **[choice]** remain to be reviewed by Céline.

**What the editor is.** A component of the shell that edits one document in the v2 block format
(ch. 03) in memory, rendered by vello, text laid out by parley. It owns no storage, opens no
connection and writes no file.

**What the host gives it, and nothing else.**
- the document (title, v2 content, trust state) and a save function — the document service
  (contract C-DOC), which encrypts, commits and runs personal-data ingest;
- input events: keys, text input, input-method composition (pre-edit and commit), pointer;
- a clipboard capability (read, write);
- notice of a remote change to the open document (sync);
- an accessibility sink (AccessKit).

**What it guarantees** — each line is a test.
1. **Nothing typed is lost.** Every character entered is in the in-memory model until the user
   removes it; a save writes exactly that model; a failed save keeps it and says so.
2. **Unknown blocks pass through** unchanged in content and position; unchanged blocks keep their
   ids and bytes (ch. 03, stable serialisation).
3. **No plaintext leaves memory except through the host's save.** No temp file, no swap file, no
   log line containing document text, no crash report written by Sovereign containing it.
   Operating-system crash dumps are outside its control and stated as a limit.
4. **No network.** The editor's crate depends on no networking crate (checked in CI).
5. **Caret and selection move by grapheme cluster** (emoji, combining marks, flags); word and
   line movement follow parley; in bidirectional text the arrow keys move in **visual** order
   (as parley does), while a selection always covers a logical range. *(Decided 2026-10-10.)*
6. **Input methods work**: composition text is shown in place, committed once, cancelled
   cleanly; the caret area is reported to the host for the candidate window.
7. **Personal-data tokens are atomic**: shown as their label (or the value when revealed, ch. 09),
   selected and deleted as one unit, never partly edited; copying a token copies its label
   unless revealed. **A token is a token only in a document its record is linked to** (ch. 09,
   *Where a token resolves*): the host says, per document, whether a token form is a real token
   there; anywhere else it is ordinary text, stored exactly as typed. Copy and paste inside
   Sovereign keeps the token, and the save links the record to the target document.
   *(Decided 2026-10-10; replaces an escape in the editor.)*
8. **Undo / redo** restore exactly the previous model, grouped by typing bursts; a save does not
   clear them; they are not written to disk (the commit history is the durable history).
9. **Large documents stay usable**: up to **1 MB of text** (1,000,000 bytes of UTF-8 in text
   blocks) in one document, a keystroke is painted within 16 ms (95th percentile) and opening
   with first paint takes at most 1 s; beyond the cap the document opens read-only rather than
   freezing. *(Cap and figures decided 2026-10-10; the cap must be raised later — larger
   documents will be needed.)*
10. **Accessible**: the focused text is exposed with its value, caret and selection through
    AccessKit; everything is reachable by keyboard; a password field never announces its content.

**Crash messages.** A Rust panic message can quote up to 256 bytes of the string it failed on.
The shell installs a panic hook that drops the payload, so a crash never writes document text
to stderr, a log or a report. *(Decided 2026-10-10; shell work, not the editor's.)*

**Behaviours (decided by Céline, 2026-10-10, unless dated otherwise).**
- **Two devices editing one document at the same time.**
  - ◐ **As built (v0.0.12):** both devices edit it. The last save wins, on both devices once they
    sync, and the other text is kept in the document's History (*A save that finds the document
    changed elsewhere*, below; ch. 05, *Direction and concurrent edits*). Nothing tells a device
    that the document is open on another: the editor can turn read-only for a document edited
    elsewhere, but no signal between devices drives it.
  - ○ **Decided 2026-10-23 (Céline), not built — for a later release:** not as a block. Both
    devices edit; their edits fork, and are reconciled at the next sync when they do not conflict;
    both are kept when they do. This replaces the decision of 2026-10-10 that one device edits a
    document at a time, which was never built.
- **Typing in a read-only document** shows a notice that nothing was changed, and why, instead of
  the keystrokes disappearing silently.
- **Clipboard.** Copying copies what is displayed (labels for personal-data tokens unless
  revealed). Ordinary text is not cleared during a session; a copy that contains a **revealed
  personal-data value** is cleared after 30 s (ch. 09). *(Decided 2026-10-10.)* **Any copy this
  process made is cleared at quit and when the store changes**, so it cannot cross to another
  persona *(Céline, 2026-10-24; v0.0.12 item 8)*; a copy another application has made since is
  left alone. So text copied in Sovereign cannot be pasted elsewhere after Sovereign has quit;
  a crash or a kill clears nothing, since no code runs then. The pairing code copied at enrolment carries the same exclusion marks as any other
  copy (below). **A new copy
  replaces the previous one entirely** — the clipboard holds one item. Operating systems can keep more (Windows clipboard history and cloud
  clipboard, clipboard managers on Linux), so Sovereign **marks every copy as excluded from
  clipboard history, from cloud clipboard sync and from clipboard monitoring** where the platform
  allows it (Windows: all three; Linux: the password-manager hint that KDE and some managers
  honour; others may still keep it — stated as a limit).
  A copy containing tokens also carries a Sovereign payload (record ids, never a value), so that
  a paste inside Sovereign keeps the tokens. Any application can write the clipboard, so a paste
  uses that payload **only if this Sovereign process wrote it and it is still the clipboard's
  current item** (a random value kept in memory, nothing stored); any other payload is ignored and
  the plain text is pasted. It is the one path that links a record to a new document from the
  clipboard (ch. 09, *Where a token resolves*). *(Decided 2026-10-10.)*
- **Saving: automatic, with versions.** The editor saves by itself after a short pause, and saves
  become versions in the document's history under the commit policy (contract C-DOC); Ctrl+S
  saves at once. The unsaved prompt remains for the case where a save fails. Cancel on that prompt
during a quit ends the quit and withdraws every Discard chosen during it: those documents' edits
count as unsaved again, in their windows (v0.0.12 lot 1, D1; cloud review of v0.0.11, finding 6).
  So a new quit asks again for them, and a restore, a skill, Delete and the orphans' trash refuse
  them as unsaved, as for any unsaved document (D2). Otherwise the prompt is unchanged (D3):
  Discard when closing one window closes it, Discard during a quit that goes through lets the app
  exit, and Save during a quit saves, then quits.
- **A save that finds the document changed elsewhere keeps both versions, without asking**
  (decided 2026-10-12, shell and mobile alike): the text being edited is saved on the current
  revision, the other state stays in the document's History (the service versions it first), and
  a notice says so. Only if that save conflicts again does the user choose (keep mine / load the
  stored version), with autosave paused until then.
- **Colours follow the theme** (decided 2026-10-12): the editor takes its palette from the shell's
  theme, every pair meeting WCAG 2.1 AA (text 4.5:1, caret, selection and accents 3:1). In the dark
  theme the selection is a bright blue with dark text on it — the only way for the highlight to
  reach 3:1 against the background while keeping selected text readable.
- **Han text falls back across the CJK fonts.** Without a language, Windows offers one fallback
  font for Han (Japanese, Yu Gothic), which lacks Cantonese characters such as 佢; the editor's
  fallback list adds the system's answers for zh-CN, zh-TW, zh-HK, ja and ko, the first font still
  winning wherever it has the glyph. (Found in the manual run of 2026-10-11.)
- **Text model: markdown source** in `text` blocks, shown with light formatting (headings,
  emphasis, lists, links) while the source stays editable; rich spans can come later as another
  `markup` value.
- **Lists continue on Enter** (decided 2026-10-14, after the manual run): Enter at the end of, or
  inside, a non-empty list item starts the next item with the same marker (`-`, `*`, `+`), the
  next number for an ordered list (`1.` → `2.`, keeping `.` or `)`), the same indentation, and an
  unchecked box for a task item (`- [ ]`). Enter on an empty item ends the list: its marker is
  removed and the line becomes empty. Shift+Enter inserts a plain line break inside the item. The
  continuation is ordinary text in the source (it is undone in one step with the Enter that made

## Canvas axes

**Status:** ✅ Desktop: X = time, Y = lane. Mobile: time vertical, lanes paged horizontally.

The canvas is a 2D map viewed through a movable, zoomable viewport. On the desktop, **X is real
time** (left = past, right = future) and **Y is the intent thread**. On mobile the same two
axes are turned: time runs down from "now" at the top, and one lane fills the screen, paged
horizontally (*Mobile UI*). In both, layout is derived, not stored: a card's time position
comes from the document's `modified_at`, its lane from its thread.
### X — calibrated time

**Status:** ✅ Built (code: `crates/sovereign-shell/src/canvas.rs`).

One day is `WORLD_PER_DAY` = 220 world units, so a card's X is a real position in time and the
ruler shows real dates. World X = 0 is the oldest document (or seven days ago in an empty
workspace). The ruler's interval adapts to zoom — minutes, hours, days, months, years — chosen
so ticks stay at least 76 px apart. A "now" line sits at the current time. On mobile the
scale is 100 px per day by default, changed by pinch (*Mobile UI*).

**The ruler across a daylight-saving change — built in v0.0.12.**
- **No panic in the repeated hour** (merged `37f303b`, 2026-10-24; no contract; PANDA2's fix,
  the laptop's second position). The ruler aligned its left edge by
  setting the local second, minute and hour, which has no answer when the local time falls in the
  hour repeated when clocks go back; the desktop window panicked whenever the ruler's left edge was
  in that hour, in v0.0.11 too. It now aligns by subtracting durations from the instant, and takes
  the earlier instant of a repeated midnight; ordinary days are unchanged. No v0.0.11 erratum
  (Céline, 2026-10-25: "Trop tard pour l'ajouter, c'est déjà passé. Il faudra corriger avant
  l'année prochaine"); the fix shipped in v0.0.12.
- **The days follow the calendar** (merged `41e45af`, 2026-10-25; found by the laptop in a frame
  of the 25-hour day, which read Oct 25 twice; PANDA2's contract, the laptop's second position).
  At the 1-, 2- and 7-day intervals each
  tick is the local 00:00 of a date (the earlier one if 00:00 occurs twice, the date's first instant
  if it does not exist), and ticks are 1, 2 or 7 calendar dates apart, counted from the left
  edge's date, so on 23-, 24- and 25-hour
  days alike every date is labelled once. At the 2-, 3-, 6- and 12-hour intervals ticks are the
  local hours that are multiples of the interval, date by date; a repeated hour gives only its
  earlier instant, a skipped hour no tick (PANDA2's choice, agreed by the laptop), so the labels
  read 00:00, 06:00, 12:00, 18:00 on both sides of a change. Minute and 1-hour ticks stay fixed
  durations (at the autumn change the 1-hour ruler shows 02:00 twice, an hour apart, both real).
  Ticks are always strictly increasing and inside the visible range; on days without a change the
  ticks and labels are as before.

## Dense clusters: bounded decks

**Status:** ✅ Desktop shell, as in the frozen Svelte desktop (code:
`crates/sovereign-shell/src/canvas.rs` `deck_roles`). Mobile stacks same-time cards by
push-down, no decks (*Mobile UI*).

When many documents share a moment in one lane, they form a **deck** that never leaves its
lane and always says how many it holds.

- **Containment.** A deck's cards stay inside their lane band at every zoom. The front card
  sits at its true position; up to three older cards peek up-left behind it, dimmed; the rest
  are hidden. The invariant `(DECK_VISIBLE − 1) · DECK_PEEK ≤ (LANE_H − CARD_H) / 2` keeps the
  fan inside the lane (4 visible, 5 world units per peek).
- **Zoom dissolves decks.** Grouping is decided in screen space at the current zoom: within a
  lane, time-ordered cards less than one card-width apart on screen share a deck. Zooming in
  separates them into single cards, down to minutes and seconds; only identical timestamps
  stay decked.
- **Total-count badge.** The front card of every multi-card deck carries the deck's **total**
  count ("12"), not the hidden remainder — one number to read instead of a sum. The badge is
  also the way to open the deck.
- **Tethered fan.** Opening a deck lifts its cards above a dimmed canvas into a readable
  column drawn in screen space (fixed size at any zoom), each with a faint tether line back to
  its true point in time; clicking a lifted card opens it; clicking away or Esc collapses.

*Replaces:* the unbounded cascade (Svelte desktop) and full occlusion (shell) of v0.0.8, and
the containment spec's "badge only on overflow" — the built badge is on every multi-card deck.

◐ In the shell the badge exists only at the full-card tier, so a deck seen below zoom 0.6
cannot be fanned there. ○ A per-lane "expand height" toggle was parked as the escalation if
the fan proves insufficient.

## Confirmation UX

**Status:** ○ Decided 2026-10-10 (Céline), not built — the shell still asks in a modal (ch. 08,
*Conversational confirmation*).

**Decided 2026-10-10 (Céline):** confirmation happens in the chat; a modal only for the highest
severity, Destruct; silence counts as consent only for an action whose undo exists, said before
acting (ch. 08 holds the rule and its precisions).

**Built.** When the orchestrator proposes a Modify, Transmit or Destruct action (ch. 08), the
shell raises a **modal**: a badge in the gravity colour, the proposal's plain-language
description, Approve and Reject. It is the topmost layer; Esc rejects; clicks outside it are
swallowed, so a decision is required. A workflow the user has already trusted does not raise
it (trust calibration, ch. 08). The outcome is echoed as a line in the chat. A proposal left
unanswered is rejected after 120 seconds; the modal closes itself 10 seconds before that, so a
late answer never reaches the next proposal. An answer (a click or Esc) counts only for the
prompt drawn on screen, and only once it has been on screen for 400 ms: a prompt that replaces
another under the cursor does not take the click aimed at the one before. The injection decision
prompt follows the same two rules. Detected injection attempts are shown in a notice,
and in the agent loop the user picks how the flagged item is handled (ch. 08).

The mobile UI shows the same proposal as a modal (the Svelte confirmation dialog, an
accessible alert dialog with a focus trap), and also offers Approve / Reject in the chat sheet
and accepts a typed "yes" / "no"; the sheet opens fully for Modify and Destruct proposals.

**Delete from the canvas** is one click, on the desktop and on the phone (Céline, 2026-10-17;
*Context menu*, ch. 03): the document goes to the trash, kept 30 days, and the notice offers Undo
for 10 seconds. The person's own Delete does not go through the action gate.

○ Not built under that decision: confirmation in the chat for Modify and Transmit, and silence as
consent; today a modal asks for Modify, Transmit and Destruct alike, and silence rejects after
120 s.

- **Each notice button names its object** (WCAG 2.4.6), and its accessible name begins with its
  visible text (2.5.3, so speech input can say what it sees): "See the alert" / "See the alerts";
  "See it: the document waiting for a decision" / "See them: the documents waiting for a
  decision"; "See it: the document that could not be read" / "See them: the documents that could
  not be read". The visible text stays short, since the notice's own text says what "it" is
  (PANDA2's choice). Before, the last two pairs were indistinguishable in a list of buttons.
- **The chat is announced** (4.1.3): the message list is a log named "Conversation", which does
  not speak by itself (`aria-live` off); a new
  assistant or system message — a reply, an action's outcome line, an approval's result — is
  announced once, politely, by a separate live region; the person's own messages are in the log but
  not announced again (PANDA2's choice). Nothing is announced at first render or when the list is
  replaced. A reply that arrives while the desktop chat panel is hidden, or while the phone's chat
  sheet is at its peek height, is announced too: the person asked for it (PANDA2's choice). Before,
  no chat message reached a screen reader.
- The frontend type-checks with no error (`svelte-check`), and the pre-publish gate keeps it there
  (`_prepublish.bat`, step 7b).
