# 12 — User Interface & Canvas: desktop (shell) and mobile

How the user sees and moves through the workspace: the native shell and its widget stack, the
window metaphor, the spatial canvas and its encoding, theming, the AI bubble, how actions are
confirmed, the mobile UI, and the accessibility commitments.

Two user interfaces ship over the same backend:

- **Desktop — the native shell** (`sovereign`), the only desktop UI since 2026-10-09 (ch. 02).
  It is the reference for desktop behaviour, and the sections below describe it unless they say
  otherwise.
- **Mobile — the Svelte UI** in the Android app, hosted by Tauri. It has its own section
  (*Mobile UI*); where a desktop section's subject also exists on mobile, the difference is
  stated there.

The Svelte desktop layout (`sovereign-tauri`) is frozen and not shipped. It is mentioned only
where an earlier design was built there.

## Native shell stack

**Status:** ✅ Built (code: `crates/sovereign-shell/`).

The shell draws everything — canvas and chrome — with one renderer, so there is no seam
between a canvas engine and a widget toolkit.

| Concern | Choice |
|---|---|
| Rendering | vello 0.9 on wgpu |
| Text shaping and layout | parley 0.10 |
| Windowing and input | winit 0.30 |
| Widgets, layout, focus, scrolling | Own thin layer on the above. Manual layout; each panel computes its geometry in one function shared by the painter and the hit-test, so the two cannot drift. No taffy yet. |
| Accessibility | accesskit 0.24 + accesskit_winit 0.32 |
| Embedded web page | `wry` child webview over the window; vello draws the browser chrome (ch. 10) |
| Clipboard, QR | arboard; qrcode drawn as vello cells |

The UI is laid out in logical pixels and scaled by the display scale factor times a user UI
scale, so it stays crisp on high-DPI screens. The widget layer was a deliberate choice over
Masonry/Xilem (pre-1.0, mid-refactor onto a different vello version) and GPUI (a second
renderer beside the canvas). The cost accepted: text input, IME, focus, scrolling and
accessibility are ours to build. ◐ Text input today has an end-pinned caret only — no
selection, no general clipboard, no IME (backlog).

*Replaces v1.x:* "UI framework: Iced 0.14" — retired in v0.0.3; the Svelte + Tauri UI was the
only UI until the native shell became the default in v0.0.8, and the shell has been the only
desktop UI since 2026-10-09 (ch. 02).

## Floating multi-window

**Status:** ✅ Built (code: `crates/sovereign-shell/src/app.rs`, `panels.rs`).

Every panel is a free-floating window over the live canvas — documents, version history,
inbox, chat, search, settings, models & trust, personal data, browser, devices & sync, review
of synced changes. Windows overlap, are dragged by their title bar, come to the front on
click, close with × or Esc, and open in a cascade. Launchers open-or-focus (a second press
closes); a document opens-or-focuses by id, so several documents can be open at once. The
chat opens anchored to the bubble, because the chat *is* the conversation with it. The
browser's webview is shown only while its window is on top and no modal is up.

| Key | Opens | Key | Opens |
|---|---|---|---|
| `c` | Chat | `b` | Browser |
| `i` | Inbox | `d` | Devices & sync |
| `s` | Settings | `r` | Synced changes to review |
| `m` | Models & trust | `g` | Enrol a recovery guardian |
| `p` | Personal data | `Ctrl+F` | Search |
| `e` / `w` | Email setup / compose (switched off in v0.0.9) | `Ctrl+S` | Save the document being edited |

◐ `Ctrl+N` (new document) and `Ctrl+B` (browser) are not bound.

*Replaces:* the first shell cut's single centred modal per panel (2026-06); the floating

## Documents

**Status:** ◐ Partial — read, edit, save, history and restore are built. Since 2026-10-19 (on
`main`, not released) the C-TEXT editor below is the shell's only document editor, in every
build; the plain text edit is removed (`doc/plans/EDITOR-default.md`).

**Decided 2026-10-10 (Céline): the document editor is built in-house on parley**, rendered by
vello like the rest of the shell, with no webview. A spike showed a webview editor can be
isolated on Windows only with four workarounds outside wry's API, ~185 MB per editor, no vello
overlay above it and no Wayland support (private spike record). **Method: tests first.** The
suite that can break the editor is written before the editor, by a different author than the
editor's, and asserts invariants only — nothing typed is lost; unknown block types (ch. 03)
pass through intact; no plaintext reaches the disk outside the encrypted store; no network;
input methods, grapheme clusters, bidirectional text, undo/redo, very large documents, a
document changed by sync while open, accessibility. The editor is built to make that suite
pass. Prerequisites: the v2 block schemas (ch. 03) and the text-field contract.

A document window shows the title and body, with a provenance accent. Edit turns the body into
an editable region (Save / Cancel, `Ctrl+S`, Esc cancels). A new document opens straight in
edit mode. History lists the document's commits; restoring one goes through the store, which
verifies the snapshot's integrity before applying it (ch. 03). Dragging a card onto another
lane moves the document to that lane's thread.

**New thread — named first, as in the Tauri desktop** (2026-10-17; Céline asked for the title
"as in Tauri" and for the work to continue on threads without her): the new-thread gestures open
a name field (*Thread name…*); Enter creates the thread with that name, Esc cancels, an empty name
creates nothing. Renaming a thread in place is not decided. ✅ Built on `main` 2026-10-18, not
released, in every build (not behind the editor's switch) (`doc/plans/THREAD-name.md`).

**Title — decided 2026-10-17 (Céline): as in the Tauri desktop.** The title is an editable
single-line field at the top of the document's page — it scrolls with the text, 1.1 × the body
size, semi-bold (revised the same evening, after her manual run) — editable whether or not the
body is in edit mode, shown as *Untitled* while empty, and saved with the body by the same
delayed save. The window's bar keeps the title in small type, so the open document stays named
when the page has scrolled. A
new document opens with the title field focused and selected, so its name is typed first; Enter
or Tab moves to the body. No *Rename…* row in the card menu. ✅ Built on `main` 2026-10-17, not
released, in every build since the editor became the only one (2026-10-19); contract T1–T7 in the private plan `doc/plans/TITLE-edit.md`.

*(The plain text edit these lines used to describe — no caret movement, × or Esc discarding
unsaved changes, a failed save not reported — is removed (2026-10-19). With the editor, nothing
unsaved is lost on any way out: it saves first and asks only when the save fails.)*

### The document editor — contract (C-TEXT)

**Status:** ✅ Built on `main` — the shell's only document editor in every build since 2026-10-19,
not released. Specified 2026-10-10; choices marked **[choice]** remain to be reviewed by Céline.

**What the editor is.** A component of the shell that edits one document in the v2 block format
(ch. 03) in memory, rendered by vello, text laid out by parley. It owns no storage, opens no
connection and writes no file.

**What the host gives it, and nothing else.**
- the document (title, v2 content, trust state) and a save function — the document service
  (contract C-DOC), which encrypts, commits and runs personal-data ingest;
- input events: keys, text input, input-method composition (pre-edit and commit), pointer;
- a clipboard capability (read, write);
- notice of a remote change to the open document (sync);
- an accessibility sink (AccessKit).

**What it guarantees** — each line is a test.
1. **Nothing typed is lost.** Every character entered is in the in-memory model until the user
   removes it; a save writes exactly that model; a failed save keeps it and says so.
2. **Unknown blocks pass through** unchanged in content and position; unchanged blocks keep their
   ids and bytes (ch. 03, stable serialisation).
3. **No plaintext leaves memory except through the host's save.** No temp file, no swap file, no
   log line containing document text, no crash report written by Sovereign containing it.
   Operating-system crash dumps are outside its control and stated as a limit.
4. **No network.** The editor's crate depends on no networking crate (checked in CI).
5. **Caret and selection move by grapheme cluster** (emoji, combining marks, flags); word and
   line movement follow parley; in bidirectional text the arrow keys move in **visual** order
   (as parley does), while a selection always covers a logical range. *(Decided 2026-10-10.)*
6. **Input methods work**: composition text is shown in place, committed once, cancelled
   cleanly; the caret area is reported to the host for the candidate window.
7. **Personal-data tokens are atomic**: shown as their label (or the value when revealed, ch. 09),
   selected and deleted as one unit, never partly edited; copying a token copies its label
   unless revealed. **A token is a token only in a document its record is linked to** (ch. 09,
   *Where a token resolves*): the host says, per document, whether a token form is a real token
   there; anywhere else it is ordinary text, stored exactly as typed. Copy and paste inside
   Sovereign keeps the token, and the save links the record to the target document.
   *(Decided 2026-10-10; replaces an escape in the editor.)*
8. **Undo / redo** restore exactly the previous model, grouped by typing bursts; a save does not
   clear them; they are not written to disk (the commit history is the durable history).
9. **Large documents stay usable**: up to **1 MB of text** (1,000,000 bytes of UTF-8 in text
   blocks) in one document, a keystroke is painted within 16 ms (95th percentile) and opening
   with first paint takes at most 1 s; beyond the cap the document opens read-only rather than
   freezing. *(Cap and figures decided 2026-10-10; the cap must be raised later — larger
   documents will be needed.)*
10. **Accessible**: the focused text is exposed with its value, caret and selection through
    AccessKit; everything is reachable by keyboard; a password field never announces its content.

**Crash messages.** A Rust panic message can quote up to 256 bytes of the string it failed on.
The shell installs a panic hook that drops the payload, so a crash never writes document text
to stderr, a log or a report. *(Decided 2026-10-10; shell work, not the editor's.)*

**Behaviours (decided by Céline, 2026-10-10).**
- **One device edits a document at a time.** There is no collaboration yet, so a document being
  edited on one device is not edited on another in parallel. Opening it for editing on a second
  device shows a warning — *this document is open in the editor on <device>* — with three choices:
  **[Switch editing to this device]** (the other device's editor turns read-only, after saving
  what it has), **[Read only]**, **[Cancel]**. On the device that loses editing, the editor turns
  read-only and anything typed there shows a warning — *this document is now being edited on
  <device>* — instead of disappearing silently; the same holds for every read-only state.
  *(Decided 2026-10-10.)* This needs a small "editing on" signal between
  paired devices over sync (ch. 05). When the devices cannot reach each other, the signal cannot
  arrive: both may edit, and the next sync falls back to the non-destructive review of ch. 05 —
  nothing is dropped.
- **Clipboard.** Copying copies what is displayed (labels for personal-data tokens unless
  revealed). No automatic clearing of ordinary text; a copy that contains a **revealed
  personal-data value** is cleared after 30 s (ch. 09). *(Decided 2026-10-10.)* **A new copy
  replaces the previous one entirely** — the clipboard holds one item. Operating systems can keep more (Windows clipboard history and cloud
  clipboard, clipboard managers on Linux), so Sovereign **marks every copy as excluded from
  clipboard history, from cloud clipboard sync and from clipboard monitoring** where the platform
  allows it (Windows: all three; Linux: the password-manager hint that KDE and some managers
  honour; others may still keep it — stated as a limit).
  A copy containing tokens also carries a Sovereign payload (record ids, never a value), so that
  a paste inside Sovereign keeps the tokens. Any application can write the clipboard, so a paste
  uses that payload **only if this Sovereign process wrote it and it is still the clipboard's
  current item** (a random value kept in memory, nothing stored); any other payload is ignored and
  the plain text is pasted. It is the one path that links a record to a new document from the
  clipboard (ch. 09, *Where a token resolves*). *(Decided 2026-10-10.)*
- **Saving: automatic, with versions.** The editor saves by itself after a short pause, and saves
  become versions in the document's history under the commit policy (contract C-DOC); Ctrl+S
  saves at once. The unsaved prompt remains for the case where a save fails.
- **A save that finds the document changed elsewhere keeps both versions, without asking**
  (decided 2026-10-12, shell and mobile alike): the text being edited is saved on the current
  revision, the other state stays in the document's History (the service versions it first), and
  a notice says so. Only if that save conflicts again does the user choose (keep mine / load the
  stored version), with autosave paused until then.
- **Colours follow the theme** (decided 2026-10-12): the editor takes its palette from the shell's
  theme, every pair meeting WCAG 2.1 AA (text 4.5:1, caret, selection and accents 3:1). In the dark
  theme the selection is a bright blue with dark text on it — the only way for the highlight to
  reach 3:1 against the background while keeping selected text readable.
- **Han text falls back across the CJK fonts.** Without a language, Windows offers one fallback
  font for Han (Japanese, Yu Gothic), which lacks Cantonese characters such as 佢; the editor's
  fallback list adds the system's answers for zh-CN, zh-TW, zh-HK, ja and ko, the first font still
  winning wherever it has the glyph. (Found in the manual run of 2026-10-11.)
- **Text model: markdown source** in `text` blocks, shown with light formatting (headings,
  emphasis, lists, links) while the source stays editable; rich spans can come later as another
  `markup` value.
- **Lists continue on Enter** (decided 2026-10-14, after the manual run): Enter at the end of, or
  inside, a non-empty list item starts the next item with the same marker (`-`, `*`, `+`), the
  next number for an ordered list (`1.` → `2.`, keeping `.` or `)`), the same indentation, and an
  unchecked box for a task item (`- [ ]`). Enter on an empty item ends the list: its marker is
  removed and the line becomes empty. Shift+Enter inserts a plain line break inside the item. The
  continuation is ordinary text in the source (it is undone in one step with the Enter that made
  it).

## Inbox — contact first

**Status:** ◐ Partial — reading is built; mark-read and sending are not (email is dormant).

conversations. Each row: avatar (same stable hue as the taskbar), name, channels

## Theme

**Status:** ✅ Built — dark and light (code: `crates/sovereign-shell/src/theme.rs`,
`frontend/src/lib/theme/colors.ts`).

Every structural colour — backgrounds, borders, dividers, text levels, the brand accent, the

## Canvas axes

**Status:** ✅ Desktop: X = time, Y = lane. Mobile: time vertical, lanes paged horizontally.

The canvas is a 2D map viewed through a movable, zoomable viewport. On the desktop, **X is real
time** (left = past, right = future) and **Y is the intent thread**. On mobile the same two
axes are turned: time runs down from "now" at the top, and one lane fills the screen, paged
horizontally (*Mobile UI*). In both, layout is derived, not stored: a card's time position
comes from the document's `modified_at`, its lane from its thread.
### X — calibrated time

**Status:** ✅ Built (code: `crates/sovereign-shell/src/canvas.rs`).

One day is `WORLD_PER_DAY` = 220 world units, so a card's X is a real position in time and the
ruler shows real dates. World X = 0 is the oldest document (or seven days ago in an empty
workspace). The ruler's interval adapts to zoom — minutes, hours, days, months, years — chosen
so ticks stay at least 76 px apart. A "now" line sits at the current time. On mobile the
scale is 100 px per day by default, changed by pinch (*Mobile UI*).

### Y — thread lanes

**Status:** ◐ Partial — lanes are built; the shell shows at most 12.

**Decided 2026-10-10 (Céline):** every thread gets its own lane, with no cap; the lane area
scrolls vertically. Two further aids are wanted: (A) at low zoom, lanes are grouped or shown as
a heat map with details on hover; (B) search and filters narrow which lanes and documents are
shown. Order: one lane per thread with vertical scroll first — it also fixes the misfiling
below — then search and filters, then the low-zoom grouping or heat map, which is the larger
piece.

Each thread is a lane, labelled by a sticky pill. Named lanes render even when empty, so a new
workspace shows its structure. Documents whose thread cannot be resolved go to an "Unfiled"
lane rather than piling into another. Dragging a card vertically onto another lane re-threads
it; X stays locked to time.

◐ The shell maps threads onto 12 fixed lanes. Up to 12 threads this is one lane per thread.
With more than 12 threads, lanes are shared and documents are misfiled:

- a shared lane is labelled with only one of its threads (the last mapped);
- a new document created in a shared lane, or a card dragged onto it, goes to the first thread
  mapped to that lane, which may not be the one the user sees named;
- a card cannot be moved between two threads that share a lane;
- from 12 threads on, the "Unfiled" lane merges into the last lane without its own label;
- the status bar's thread count stops at 12, and the accessibility summary always announces
  12 lanes.

The lane model needs one mapping used by drawing, drag, new document, status bar and
accessibility, and a rule for workspaces with many threads (backlog). The mobile UI pages
through one lane per thread, without a cap.

### Home and fit

**Status:** ✅ Built (code: `crates/sovereign-shell/src/app.rs`).

- **Home (`h`)** — the present: lanes fitted to about three quarters of the canvas height
  (zoom bounded to 0.08–1), "now" at the horizontal centre. Used on login, after onboarding and
  after creating a document. At ordinary lane counts this gives a day- or hour-grained ruler.
- **Fit (`f`)** — every document in view, zooming out as needed but never in past the default
  0.6. Used on load and after a sync brings documents in.

On mobile each lane opens at "now" (the top of the lane); there is no home or fit command.

### Retired: semantic 3D positioning

**Status:** ✗ Retired — replaced by the time × lane canvas above.

v1 specified a 3D space: X/Y by semantic proximity, Z as time depth, positions 99%
AI-generated with user override, stored per snapshot so documents could move through space as
a project evolved. None of it was built, and the consolidated design decisions fixed the axes
to time and threads. The `spatial_x` / `spatial_y` fields still exist on the stored document;
no UI lays cards out from them. Semantic proximity is carried by relationships and by
consolidation's suggested links, drawn as edges between cards (ch. 03).

*Replaces v1.x:* §Spatial Positioning (3D, semantic X/Y, time as Z, AI-placed, per-snapshot).

## Dense clusters: bounded decks

**Status:** ✅ Desktop shell, as in the frozen Svelte desktop (code:
`crates/sovereign-shell/src/canvas.rs` `deck_roles`). Mobile stacks same-time cards by
push-down, no decks (*Mobile UI*).

When many documents share a moment in one lane, they form a **deck** that never leaves its
lane and always says how many it holds.

- **Containment.** A deck's cards stay inside their lane band at every zoom. The front card
  sits at its true position; up to three older cards peek up-left behind it, dimmed; the rest
  are hidden. The invariant `(DECK_VISIBLE − 1) · DECK_PEEK ≤ (LANE_H − CARD_H) / 2` keeps the
  fan inside the lane (4 visible, 5 world units per peek).
- **Zoom dissolves decks.** Grouping is decided in screen space at the current zoom: within a
  lane, time-ordered cards less than one card-width apart on screen share a deck. Zooming in
  separates them into single cards, down to minutes and seconds; only identical timestamps
  stay decked.
- **Total-count badge.** The front card of every multi-card deck carries the deck's **total**
  count ("12"), not the hidden remainder — one number to read instead of a sum. The badge is
  also the way to open the deck.
- **Tethered fan.** Opening a deck lifts its cards above a dimmed canvas into a readable
  column drawn in screen space (fixed size at any zoom), each with a faint tether line back to
  its true point in time; clicking a lifted card opens it; clicking away or Esc collapses.

*Replaces:* the unbounded cascade (Svelte desktop) and full occlusion (shell) of v0.0.8, and
the containment spec's "badge only on overflow" — the built badge is on every multi-card deck.

◐ In the shell the badge exists only at the full-card tier, so a deck seen below zoom 0.6
cannot be fanned there. ○ A per-lane "expand height" toggle was parked as the escalation if
the fan proves insufficient.

## The AI bubble

**Status:** ◐ Partial — the bubble and its styles are built; its states are shown only in part.

The orchestrator is always present as a floating bubble, bottom right, above the taskbar.
Clicking it opens the chat. Its look is one of nine styles chosen at onboarding or in
Settings (Icon, Wave, Spin, Pulse, Blink, Rings, Matrix, Orbit, Morph); in the shell they are
static re-creations, since vello has no SVG animation runtime.

The bubble shows what the AI is doing, using the provenance language (Appendix B §3):

| State | Intended treatment |
|---|---|
| Idle | Subtle pulse, neutral accent |
| Processing owned content | Owned-blue glow |
| Processing external content | External-red glow and a parallelogram cue |
| Proposing | Accent highlight, the proposal visible |
| Executing | Progress, the skill's name |
| Suggesting | A count of pending suggestions |

The orchestrator emits all six states. The shell ignores the state events: its ring breathes
while a chat reply is pending, and is otherwise idle. The mobile UI has no bubble: the chat
sheet's collapsed row shows "Thinking…" or the pending action's level, and a count of pending
link suggestions (*Mobile UI*).

○ Not built in either shipped UI: the external-content cue. It is the security half of the
bubble — an unusual proposal made while external content is being processed should be visible
as such.

## Confirmation UX

**Status:** ⚠ Conflict — decision pending; a modal is built where Appendix B asks for
conversation.

**Built.** When the orchestrator proposes a Modify, Transmit or Destruct action (ch. 08), the
shell raises a **modal**: a badge in the gravity colour, the proposal's plain-language
description, Approve and Reject. It is the topmost layer; Esc rejects; clicks outside it are
swallowed, so a decision is required. A workflow the user has already trusted does not raise
it (trust calibration, ch. 08). The outcome is echoed as a line in the chat. A proposal left
unanswered is rejected after 120 seconds. Detected injection attempts are shown in a notice,
and in the agent loop the user picks how the flagged item is handled (ch. 08).

The mobile UI shows the same proposal as a modal (the Svelte confirmation dialog, an
accessible alert dialog with a focus trap), and also offers Approve / Reject in the chat sheet
and accepts a typed "yes" / "no"; the sheet opens fully for Modify and Destruct proposals.

**Delete from the canvas** is a two-step confirm in the shell's context menu.
◐ The shell's delete path does not yet go through the action gate or the soft-delete undo
window (backlog). On mobile, Delete in the long-press menu is a soft delete (ch. 03) with no
confirmation step.

> ⚠ **Conflict — decision pending (Céline).** Appendix B §1–2: Modify confirmed *in the conversation* (with silence as consent after 5 s), Destruct as a modal *with a 30-day undo window* vs built: a modal for Modify, Transmit and Destruct alike, silence = reject after 120 s, and a two-step inline confirm for canvas Delete without the undo window.

## Onboarding and the auth gate

**Status:** ✅ Built (code: `crates/sovereign-shell/src/onboarding.rs`, `panels.rs`).

Until login, a full-screen gate owns the keyboard and the canvas is not drawn. First launch
runs an eight-step wizard: welcome (start fresh or pair with an existing device), name the AI,
bubble style, theme, sample data (opt-in), password with a strength meter, optional duress
password, optional canary phrase. Paired devices skip sample data. The security content of
these steps is ch. 07; recovery from the login screen is ch. 06.

The mobile UI uses the Svelte login screen and onboarding wizard.

**While the account is being created** (decided by Céline 2026-10-19, for v0.0.11 rc2; to be
built in the mobile wizard). The wizard shows that it is working — a spinner and a line saying
what is happening — and every button that could start or leave account creation ("Get started",
"Skip", "Back") is disabled until it ends; if it fails, the error is shown on the screen, not only
in a log. This is one layer; the backend refuses a second request anyway (ch. 07, *Auth store*).
As built, the desktop wizard creates the store on its window's own thread: a second click cannot
start another, but the window shows nothing while it waits (a limitation, to be given the same
feedback later).

**Text fields of the auth gate, the wizard and the search window are readable in both themes**
(decided by Céline 2026-10-19, for v0.0.11 rc2; to be built): their text is drawn at **4.5:1 or
more** against the field's fill (WCAG 1.4.3), the fill being the palette's input colour. The
search box had the same fill (`draw_search`). *Why:* on rc1 the fields
were filled with the colour meant for text on a coloured button; in the dark theme typed text and
password dots were nearly invisible (about 1.2:1), in the setup wizard and on the login screen.

### Canvas

**Status:** ✅ Built (code: `mobile/MobileCanvas.svelte`, `mobile/LaneHeader.svelte`,
`mobile/LaneSwitcherSheet.svelte`, `frontend/src/lib/stores/canvas.svelte.ts`).

- **Time runs down.** A sticky "Now" marker sits at the top of each lane; a card's distance
  below it is its age (`now − modified_at`) times the scale. The default scale is 100 px per
  day; the layout re-derives every 15 minutes as time passes.
- **One lane per screen, paged.** Each thread is a lane that fills the screen. A horizontal
  swipe pages to the next or previous lane, committing on a quarter-screen drag or a fling;
  swipes from the left edge are left to the system. The lane header shows the lane's name and
  one dot per lane; tapping (or long-pressing) the name opens a switcher listing every thread
  with its document count. There is no cap on the number of lanes.
- **Push-down stacking, no decks.** Cards that would overlap — documents modified at nearly the
  same time — are pushed down one below the other, so a pushed card sits lower (older-looking)
  than its true time. There is no deck, fan or count badge.
- **Zoom.** A two-finger vertical pinch changes the time scale (5 – 2,000 px per day), anchored
  at the fingers' midpoint so the time under them stays put. `+` / `−` buttons do the same for
  a pointer or assistive technology.
- **Density view.** Below 30 px per day the canvas switches to an all-lanes overview: one
  column per thread with its total, and a heatmap of day buckets (up to a year). Tapping a
  column opens that lane at the default scale.
- **Cards.** Title, relative time ("2h ago"), the provenance bar (below), and a `↔N` badge
  counting links to documents in other lanes. Edges between cards are not drawn. A tap opens
  the document reader; a long press opens the context menu: Open, Move to thread, Delete (a
  soft delete, ch. 03, without a confirmation step).

◐ Not on mobile: decks, edges, milestones, a minimap, home and fit.

## Accessibility

**Status:** ◐ Partial — the commitments below are design constraints; on the desktop the
screen-reader path is read-only and the canvas is summarised; on mobile provenance is carried
by colour only.

**Commitment: WCAG 2.1 AA, as a design constraint, not a retrofit** — in both shipped UIs.
The table covers the desktop shell; mobile is summarised after it.

| Criterion | Requirement | Native shell |
|---|---|---|
| 1.4.1 Use of colour | Meaning never by colour alone | ✅ Provenance by shape (rectangle / parallelogram; circle / diamond at low zoom). |
| 1.4.3 Contrast | Text ≥ 4.5:1 | ◐ Dark theme: secondary text about 5.4:1 on panels, smallest text 12 px. Below the bar: the deck count badge (about 2.1:1 dark, 3.2:1 light) and hint text (about 4.0:1 dark, 3.0:1 light). |
| 1.4.4 Resize text | 200% without loss | ✅ `Ctrl +/−/0` UI scale 0.6–3.0, DPI-aware layout. |
| 1.4.11 Non-text contrast | Controls ≥ 3:1 | ◐ Focus and active borders meet it; the thin scrollbar (about 2.45:1 in the dark theme) does not. |
| 2.1.1 Keyboard | Everything operable by keyboard | ◐ Canvas pan, zoom, home and fit; launchers; search; save; Esc; Tab between auth fields. Canvas keys work only when no window is open; cards cannot be focused or opened by keyboard; the context menu and taskbar are pointer-only. |
| 2.4.7 Focus visible | Visible focus | ✅ Accent border and caret on the focused field. |
| 4.1.2 Name, role, value | Exposed to assistive technology | ◐ See below. |

**Screen reader (AccessKit).** The shell builds an accessibility tree every frame and hands it
to the OS screen-reader API: a window root and one node per readable or focusable element of
the active screen — auth fields with focus, chat messages and composer, the lines of the
inbox, settings, search results, history, models, personal data, devices and review windows,
the recovery wizard, and a count of other open windows. **Password fields never expose their
contents: only the number of characters is announced.** The pairing PIN is read aloud, as it is
a short-lived code meant to be shared.

◐ Gaps: actions are not handled, so a screen reader can read and follow focus but cannot
activate controls; the canvas is exposed as one summary line, not one node per card, and that
line always announces 12 thread lanes whatever the workspace holds; the AI action
confirmation, the injection decision prompt, notices, the context menu and the onboarding
wizard are not in the tree; validation with Narrator has not been done.
○ Touchscreen and trackpad pinch gestures in the shell.

**Mobile.** The Svelte components use native buttons and ARIA labels and roles; lanes other
than the visible one are hidden from assistive technology; `+` / `−` buttons stand in for the
pinch; taskbar targets are at least 48 px. ◐ 1.4.1 is not met visually: provenance is a colour
bar (*Provenance on mobile*). [unverified] Text contrast on mobile and behaviour with
TalkBack.
